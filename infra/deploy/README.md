# Deployment (CD): Render + Neon

The API runs as a Docker container on **Render**; the web version of the app is a Render **static site**; the database is **PostgreSQL 16 on Neon**. The Android app and the web app both call the API over HTTPS.

| Live | URL |
| :--- | :--- |
| Web app | https://digitalmohalla-web.onrender.com |
| API (health check, interactive docs at `/docs`) | https://digitalmohalla-api.onrender.com/health |

| Part | Where | Defined in |
| :--- | :--- | :--- |
| API image (FastAPI + Alembic migrations) | Built by Render from `backend/` | `backend/Dockerfile`, `backend/.dockerignore` |
| Web service settings | Render, free plan, Singapore | `render.yaml` (Render Blueprint) |
| Web app (Expo web export, static files) | Render static site on Render's CDN, built from `frontend/` | `render.yaml` (`digitalmohalla-web`) |
| Database | Neon, PostgreSQL 16, AWS Singapore | Connection string stored only as the Render secret `DATABASE_URL` |

## How a deploy happens

1. A pull request from `develop` is merged into `main`.
2. CI (`.github/workflows/ci.yml`) runs on that commit.
3. Render waits for the checks (`autoDeployTrigger: checksPass`). If they pass and the commit changed something under `backend/`, Render builds the image; if it changed something under `frontend/`, Render rebuilds the web app (`npx expo export --platform web`).
4. The new container runs `alembic upgrade head` (applies only new migrations), then starts the API.
5. Render calls `/health`. Only when it answers does the new version replace the old one. If the build, a migration or the health check fails, the previous version stays live.

**Rollback:** Render dashboard → the service → Events → pick an earlier deploy → Rollback. Migrations are forward-only, so a rollback must not depend on undoing one: make schema changes additive (add first, remove in a later release).

## One-time setup

### 1. Neon (database)

1. Sign in at neon.com and create a project: PostgreSQL **16**, region **AWS Asia Pacific (Singapore)**.
2. Open **Connect**, turn **Connection pooling off**, and copy the connection string. The host must not contain `-pooler`: the API sets `search_path` per connection and runs migrations, and the pooled endpoint supports neither.
3. Turn it into the SQLAlchemy form by changing the scheme to `postgresql+psycopg://`:

   ```text
   postgresql+psycopg://<user>:<password>@<endpoint>.ap-southeast-1.aws.neon.tech/<database>?sslmode=require
   ```

4. From your PC, apply the schema and add the synthetic demo users once (`DATABASE_URL` in the shell overrides `backend/.env`):

   ```powershell
   cd backend
   $env:DATABASE_URL = "<the Neon URL from step 3>"
   uv run alembic upgrade head
   uv run python ../scripts/seed_demo.py      # no --reset: it would wipe the deployed data
   Remove-Item Env:DATABASE_URL
   ```

   If `alembic upgrade head` fails on `CREATE ROLE dm_app` or a `SECURITY DEFINER` function, stop and tell the team: the schema needs a small change for managed PostgreSQL.

### 2. Render (API)

1. Sign in at render.com with GitHub and give Render access to the `DigitalMohalla` repository (the repository owner may have to approve it).
2. **New → Blueprint**, select the repository and branch `main`. Render reads `render.yaml`.
3. When asked for `DATABASE_URL`, paste the Neon URL from step 1.3. `JWT_SECRET` is generated by Render.
4. Apply. The first deploy builds the image (a few minutes). Then open `https://<service-name>.onrender.com/health`; it should return `{"status":"ok"}`.

### 3. The web app

Created by the same Blueprint (`digitalmohalla-web`); nothing to enter. Notes:

- `EXPO_PUBLIC_API_URL` is built into the JavaScript at build time. Changing it needs a rebuild, not a restart.
- One rewrite rule sends every path without a file (`/login`, `/item/<id>`) to `index.html`; Expo Router then shows the right screen, so deep links and page reloads work.
- The API only accepts browser calls from this site's address (`CORS_ORIGINS` on the API service). If the site ever gets a different address, update that value too.
- `EXPO_PUBLIC_DEMO_PASSWORD` is deliberately not set, so the deployed site shows no one-click demo logins.
- Rebuilding locally with a different `EXPO_PUBLIC_API_URL`: add `--clear`, otherwise Metro's cache keeps the old value.

### 4. The Android app

Build the app with `EXPO_PUBLIC_API_URL=https://<service-name>.onrender.com` (for EAS builds, set it in the build profile's environment).

## Smoke test after a deploy

```powershell
curl https://<service-name>.onrender.com/health
```

Then sign in on the app as `borrower@example.test` (demo password from `scripts/seed_demo.py`) and open **Browse items**.

## Free-plan limits to plan around

- The free web service **sleeps after about 15 minutes without traffic**; the next request takes about a minute while it wakes. Open `/health` a minute before a demo or evaluation.
- Neon's free plan suspends the database when idle and wakes it on the next connection within about a second; the API's connection pool reconnects by itself (`pool_pre_ping`).
- Check both providers' current free-plan limits before relying on them for an evaluation.

## Running the production image locally

```powershell
docker build -t dm-api backend
docker run --rm -p 8001:8000 -e DATABASE_URL="<url>" -e JWT_SECRET="<random>" -e CORS_ORIGINS= -e CORS_ORIGIN_REGEX= dm-api
```

Inside a container `localhost` is the container itself. For a database running on your PC use host `host.docker.internal`; for a database in another Docker Compose project, join its network (`--network <project>_default`) and use its service name as the host.
