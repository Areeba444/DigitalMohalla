## Rationale

A membership request is the gate in front of every loan: `txn_guard_create` lets a member borrow only in a community where their membership is APPROVED, so this machine decides who can take part at all. It uses exactly the six `membership_status` values already in schema v2.3, so it needs no schema change. The two undecided states sit in one composite (UNDECIDED) because the database treats them alike: `decided_at` is null exactly while a request is PENDING or AWAITING_INFORMATION, and approval, rejection and withdrawal leave from either. A locality result never moves the machine by itself; INCONCLUSIVE and CONFLICTING outcomes are evidence in the moderator queue (FR-A-08), so nobody is rejected automatically, which is the panel's location action expressed as behaviour.

**Realises:** FR-A-08, FR-A-09, FR-A-10, FR-A-11, FR-M-01 (revocation), NFR-PR-01 (no coordinates stored).
**Maps to code (to be built, F2 in the plan):** a membership service beside `domain/lifecycle/service.py`; the `membership` and `locality_verification` tables; the moderator membership queue (wireframe W11).

## States

| State | Meaning | `decided_at` | Live? (`membership_one_live_uq`) |
|---|---|---|---|
| PENDING | Request submitted with a coarse locality result; waiting in the moderator queue | null | yes |
| AWAITING_INFORMATION | The moderator asked the applicant for more evidence | null | yes |
| APPROVED | Member of the community with role MEMBER | set | yes |
| REJECTED | Refused with a reason; may be reversed (M08) | set | no |
| WITHDRAWN | The applicant withdrew the request (final) | set | no |
| REVOKED | Membership ended by a moderator or admin (final) | set | no |

## Transitions

| ID | From | Event [guard] / effect | To | Actor | Source |
|---|---|---|---|---|---|
| M01 | (start) | `join_requested` [contact verified; no live membership in this community; community active; invitation code valid] / one coarse GPS check and the invitation evaluated in memory; only the coarse outcome stored; flags attached; moderators notified | PENDING | Applicant | UC-A3 1–4, 3a–3d, 4b, 4d; FR-A-07, A-09 |
| M02 | PENDING | `info_requested` [moderator of this community; reason] / response deadline set; applicant notified | AWAITING_INFORMATION | Moderator | UC-A4 2a; FR-A-10 |
| M03 | AWAITING_INFORMATION | `info_provided` [applicant] or `deadline_passed` / note "no response" | PENDING | Applicant / system | UC-A4 2a |
| M04 | PENDING, AWAITING_INFORMATION | `approved` [moderator of this community, not the applicant; reason; applicant still active; request still undecided] / role MEMBER, `decided_at`, audit entry, applicant notified; if the stored outcome was not VERIFIED, a `MODERATOR_APPROVAL` locality result is recorded with `approved_by` (A11) | APPROVED | Moderator / admin | UC-A4 3–4, 4a, 4b, 4c; FR-A-10, A-11 |
| M05 | PENDING, AWAITING_INFORMATION | `rejected` [same guards; reason] / reason recorded, audit entry, applicant notified | REJECTED | Moderator / admin | UC-A4 3, 3a; FR-A-08, A-10 |
| M06 | PENDING, AWAITING_INFORMATION | `withdrawn` [applicant] / `decided_at` set | WITHDRAWN | Applicant | UC-A4 4c |
| M07 | APPROVED | `revoked` [moderator of this community or admin; reason] / audit entry; open loans routed to a moderator | REVOKED | Moderator / admin | FR-M-01; UC-A4 3b (reversal of an approval) |
| M08 | REJECTED | `decision_reversed` [another moderator or admin; reason] / both decisions kept in the log | APPROVED | Moderator / admin | UC-A4 3b; FR-A-11 |

Concurrency (UC-A4 4a, FR-A-11): M04, M05 and M06 apply only while the row is still undecided; a second moderator who decides later sees the current state and nothing is re-applied.

## Tests this machine implies (for test plan v2, suite 21)

- Duplicate request while a live membership exists is refused (M01 guard, `membership_one_live_uq`).
- A moderator of another community cannot decide (M04/M05 guard, NFR-S-03).
- Two moderators decide at once: one decision applies, the other sees the current state (UC-A4 4a).
- An INCONCLUSIVE or CONFLICTING locality outcome alone never produces REJECTED (FR-A-08).
- Every exit from PENDING/AWAITING_INFORMATION sets `decided_at` (`membership_decided_ck`).
- Reversal keeps both decisions in the log (M08, FR-A-11).
