## 2. Defect severity

| Severity | Definition | Examples | Response |
| :--- | :--- | :--- | :--- |
| S1 critical | Breaks a rule the project promises, loses or corrupts data, or exposes private data | Double booking; a lifecycle transition the matrix forbids is accepted; an event or audit entry can be changed without the integrity check noticing; a coordinate, address or CNIC appears in a response or log; a person is restricted with no human decision; the deployed API does not start | Stop the release. Roll back if deployed (section 5). Fix and add a regression test before anything else |
| S2 major | A core flow cannot be completed, or the engine gives a wrong state for a specified scenario | A scenario ES-01 to ES-13 gives the wrong rule, state or explanation; a dispute cannot be resolved; a scheduled job runs twice with visible effect (NFR-R-05) | No release while open. Fix within the current slice |
| S3 minor | A flow works but is wrong in a way users notice, with a workaround | Wrong wording in an explanation; a filter ignored; a screen layout broken at 390 pt | May release with the defect listed in the release note; fix in the next slice |
| S4 cosmetic | No effect on behaviour or understanding | Spacing, colour, typo in a non-safety text | Fix when convenient |

Every defect is a GitHub issue labelled with its severity, the test case that found it, and the commit that fixed it. An S1 or S2 also needs the test that would have caught it.

## 4. Deployment procedure

The as-built procedure in `infra/deploy/README.md` stays: merge to `main`; CI passes; Render builds; the container runs `alembic upgrade head`; Render switches only when `/health` answers. Iteration 2 adds the steps below, in this order.

1. **Before migration 0002.** Take a manual `pg_dump` of the Neon database and keep it outside the repository; it may contain synthetic accounts only. Check that the migration is additive (expand first, contract in a later release). Enable the `vector` extension on Neon if ADR-0016 is accepted.
2. **Secrets.** Add `JOBS_TOKEN` to the Render API service and the same value to the GitHub repository secret used by the cron workflow. Add the storage credentials to Render only. Never commit them or print them in logs.
3. **Cron workflow.** Schedule the run-due-jobs call every 15 minutes (proposed). GitHub's scheduled workflows can start late, so the jobs are written to catch up and are idempotent with a job-run key and an advisory lock (NFR-R-05). One run also wakes a sleeping service.
4. **After deploy: smoke TC-91 (extended).**
   - `/health` answers.
   - Log in as a seeded synthetic user, and one scripted request reaches ASSESSED.
   - Planned additions: one search returns results and says which mode it used; one photo upload is stored and its signed URL loads; one manual run-due-jobs call returns, and a second call changes nothing.
5. **Record.** Note the deploy, the TC-91 result and the commit in the release note (GitHub release or `docs/` changelog).

## 5. Rollback

### 5.1 What can be rolled back, and how

| Layer | How | Limit |
| :--- | :--- | :--- |
| API code | Render → the service → Events → an earlier deploy → Rollback | Works only if the older code runs on the newer schema. That is why migrations are additive |
| Web app | Same, on the static site | The API address is built in; it does not change between deploys |
| Database schema | No down-migrations. A bad migration is fixed forward with a new migration | Additive changes only; a column is dropped one release after the code stops using it |
| Database data | Restore from the `pg_dump` taken before the migration, or Neon's own restore feature. Check its retention window on the free plan before relying on it | The event store is append-only, so restoring loses events after the dump; on synthetic data this is acceptable and is stated in the release note |
| Scheduler | Disable the cron workflow in GitHub (Actions → the workflow → Disable) | Due jobs wait; they catch up when it is enabled again |
| Object storage | Files are never overwritten (each key is new), so nothing needs rolling back | Orphaned files from a failed upload are removed by a later clean-up job (iteration 3) |

### 5.2 When to roll back

- TC-91 fails after a deploy.
- An S1 is found on the deployed instance.
- An S2 blocks the demo flow.

Testing of the slice stops until the previous version is live and TC-91 plus suites 1 to 5 pass against it (Test Plan §11).

### 5.3 Rehearsal (build item M10, once before the final)

1. Deploy a commit with a deliberate, harmless fault: `/health` reports failure. Render keeps the previous version live; record this.
2. Deploy a commit that passes `/health` but fails TC-91 (one scripted request does not reach ASSESSED). Roll back by hand from the Render dashboard and time it.
3. Run TC-91 and suites 1 to 5 against the restored version.
4. Record the times, the screenshots and what was unclear in this plan, then fix the plan.

The rehearsal uses a branch merged to `main` only for the rehearsal, with the team's agreement, and is announced in the team channel first.
