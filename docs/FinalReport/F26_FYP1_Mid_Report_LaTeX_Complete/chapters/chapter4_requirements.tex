\chapter{Requirements Specification and Acceptance Criteria}

\section{Requirements Engineering Methodology and Baseline}
The requirements baseline for Digital Mohalla was developed iteratively, formalized in \texttt{DigitalMohalla\_FR\_NFR\_Ver1.md} (version 1.3), and traced directly to use cases and architecture. Requirements are grouped into distinct functional domains:
\begin{enumerate}
    \item \textbf{User Accounts \& Neighbourhood Membership (FR-A):} Secure authentication, identity verification boundaries, and role management.
    \item \textbf{Item Catalog \& Inventory (FR-I):} Resource metadata, availability scheduling, and value tier classification.
    \item \textbf{Borrowing Lifecycle \& Handover (FR-L):} Request submission, dual-party inspection, handover/return confirmation, and state tracking.
    \item \textbf{Trust \& Risk Assurance Engine (FR-T):} Bayesian posterior estimation, indirect path propagation, decision policy rules, and explanation generation.
    \item \textbf{Dispute Resolution \& Moderation (FR-M):} Conflict escalation, evidence logging, and moderator adjudication.
\end{enumerate}

\section{Non-Functional Requirements (NFRs)}
\begin{itemize}
    \item \textbf{NFR-SEC-01 (Credential Security):} User passwords must be hashed using argon2id with high memory cost parameters. Authentication tokens must be stateless signed JWTs with expiration bounds.
    \item \textbf{NFR-PRIV-01 (Location Privacy):} The system must never store, query, or expose exact street addresses or raw GPS latitude/longitude coordinates in API endpoints or persistent databases. Only coarse neighbourhood identifiers are persisted.
    \item \textbf{NFR-REL-01 (Event Store Immutability):} Transaction events must reside in an append-only PostgreSQL table protected by triggers preventing \texttt{UPDATE} or \texttt{DELETE} operations. Each event must include a cryptographic SHA-256 hash chaining back to the previous transaction event.
    \item \textbf{NFR-CONC-01 (Zero Double-Booking):} The system must prevent concurrent double-booking of any item over overlapping calendar intervals with zero false negatives, enforced via PostgreSQL \texttt{btree\_gist} exclusion constraints.
    \item \textbf{NFR-PERF-01 (Engine Response Time):} Total assurance evaluation time (direct estimation + bounded $k$-hop search) must execute within 250 milliseconds for networks up to 2,000 nodes under normal server load.
    \item \textbf{NFR-MAINT-01 (Contract Synchronization):} The mobile and web clients must maintain 100\% type synchronization with the backend through automated TypeScript client generation from the OpenAPI 3.1 specification.
\end{itemize}
